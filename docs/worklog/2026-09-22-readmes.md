# 2026-09-22 crates.io の説明を今の実物に合わせる（0.6.1、docs only）

0.6.0 を公開した直後、著者が crates.io を見て「各クレートの説明が古いようにみえる」と言った。
crates.io のページに出るのは `Cargo.toml` の `description` と、その crate の README だけである。
リポジトリの `docs/` がどれだけ正確でも、そこは release のときにしか焼き直されない。
5 つの crate それぞれについて、**ページに出る文面の主張を 1 つずつ今の木と突き合わせて**直し、
説明と README だけの patch release（`sabiruby` 0.6.1 ほか）を準備した。

ブランチは `readmes`、main の `2e5d95b` から。`.rs` は 1 行も触っていない
（`git diff main -- '*.rs' | wc -l` が 0）。

## 2. 決めたこと — release のたびに静かに古くなる書き方を減らす

0.6.0 の準備の worklog（`2026-09-22-release-0.6.md` §10-3）が、design の文書に版が直書きして
あると「次に拾い漏らす場所」になると書いている。README は crates.io の顔なので、同じことが
もっと効く。3 つ決めた。

1. **`## Status` の見出しから版と日付を落とす。** 「今」を言う節に「いつの今か」を書くと、
   直さなかった瞬間に嘘になる。どの版に何が入ったかは CHANGELOG が crate ごと・commit ごとに
   持っているので、README の先頭からそこへリンクし、「このページは今あるものを言う。版と
   日付は CHANGELOG」と 1 行で書いた。0.5.0 → 0.6.0 のときに誰もこの見出しを直さなかった、
   というのがそもそもの発端である。
2. **ベンチの数は出どころのファイル名とセットで書く。** 落とすことも考えたが、埋め込み
   ホスト向けの VM で「参照実装の何倍か」は読者が最初に知りたい数なので、落とすと README が
   弱くなる。代わりに `bench/results/96221fb.md` を名指しし、「ここの数はそのファイルの最後の
   表が言うこと」と添えた。次に測った人が README も直すための手がかりになる。
3. **機械の数は書かない。** 「clean build に約 2 s / 7 s」は測り直すと合わない（3 節）。
   合わないのは主に `codegen-units = 1`（0.5.0、`96221fb`）のせいで、あの変更は
   `sabiruby-cli` の clean release build を 9.2 s → 18.1 s にしたと
   `docs/verification/bench.md` 自身が書いている。つまりこの数は **release のたびに古くなる
   典型**だった。別の機械の秒に置き換えても同じことが起きるので、
   「C を建てるのが clean build のほとんどで、一度きり」という**順序の主張**だけ残した。

依存の例の版（`sabiruby = "0.6"` など）は caret の幅のある要求なので patch では動かない。
そのまま。

## 3. 測ったこと — C 部分の build 時間

README の「about 2 s (debug) and 7 s (release, one core)」を測り直した。
`touch compiler/build.rs` してから建て直す（C の再コンパイルだけを起こす）。24 スレッドの機械。

```
debug   rebuild: 5.18 s wall, 3.93 s user
release rebuild: 24.20 s wall, 21.93 s user
```

user ≒ wall なので、cc の並列度が効いていない（実質 1 コア）。debug で 2.6 倍、release で
3.5 倍。release 側の開きは `codegen-units = 1` で説明がつくが、debug 側はつかない —
元の数がどう測られたかが残っていないので、**再現できない数として落とす**ことにした。
新しい数を書かないのは、これがこの機械の数だからである（CLAUDE.md の「数を書くときは、その数が
どこから来たかを 1 行で言えること」を満たせない）。

## 4. `CHANGELOG.md` は既に package に入っていた

0.6.0 の worklog §10-1 は「`CHANGELOG.md` は今も `include` に入っていない。root crate の
`include` は `/src`・`/build.rs`・`/docs/**/*.md`・`/README.md`・2 つの LICENSE で、crates.io の
ページから CHANGELOG は読めない」と書いている。**これは誤りである。**

```
$ git log --oneline -S'CHANGELOG.md' -- Cargo.toml
861b133 package: CHANGELOG ships in the crate, docs.rs builds with all features   (2026-09-16)

$ cargo package --list -p sabiruby | grep CHANGELOG
CHANGELOG.md
```

`861b133`（0.5.0 の準備）で入っており、0.5.0・0.5.2・0.6.0 の tarball はどれも CHANGELOG を
含んでいる（`include` の行は v0.6.0 のタグでも同じ）。だから **`include` に足すものは無く、
CHANGELOG による大きさの増加は 0** である。`sabiruby` の package が 157 → 158 ファイル
（2.4 MiB、圧縮 767.8 KiB）になったのは、この worklog（15 KiB）が `docs/**/*.md` に入るため。
CHANGELOG 自身は 31 KiB で、0.5.0 から既にこの tarball の一部だった。

ただし「crates.io のページから CHANGELOG が読めない」という**症状のほうは本当**である。
crates.io が描くのは README だけで、tarball に CHANGELOG が入っていても描かない。docs.rs も
同じ。だから直し方は `include` ではなく**リンク**で、root README の先頭からと、CHANGELOG を
持たない 4 つの crate の README からそれぞれ 1 本、絶対 URL で張った。
`include` を疑って `cargo package --list` を引く前に worklog の記述を信じていたら、
「入れた」と報告して何も変わらないところだった。

## 5. 版

説明と README だけなので全部 patch。**文面を直した crate だけ上げる**——結果として 5 つとも
直したので 5 つとも上がる。crate のページは release のときにしか焼き直されないので、
README を直した crate は出さないと直らない。

| crate | → |
|---|---|
| `sabiruby` | 0.6.1 |
| `sabiruby-compiler` | 0.3.1 |
| `sabiruby-serde` | 0.2.1 |
| `sabiruby-cli` | 0.6.1 |
| `sabiruby-macros` | 0.1.1 |

`sabiruby-macros` は 0.5.0 で公開して以来はじめて上がる。

**workspace の中の版の要求は直していない。** 確かめた: root の
`sabiruby-macros = { version = "0.1.0" }`、compiler の `sabiruby = "0.6.0"`、cli の
`sabiruby = "0.6.0"` と `sabiruby-compiler = "0.3.0"`、serde の `sabiruby = "0.6"` —
どれも caret なので `^0.1.0` は 0.1.1 を、`^0.6.0` は 0.6.1 を、`^0.3.0` は 0.3.1 を受ける。
0.6.0 のときに 4 つの crate が揃って動かねばならなかったのは minor が上がったからで、
patch ではそれが起きない。

その帰結として、**今回は dry-run が 5 つとも先に通る**。0.6.0 のときは
「VM が index に出るまで残り 3 つは dry-run すら通らない」だったが、
`^0.6.0` は crates.io にある 0.6.0 で既に満たされているので、順序は publish の依存関係
（index に出るまでの待ち）だけの問題になる。

```
cargo test --workspace                                    250 passed, 0 failed（34 のテストバイナリ）
RUSTDOCFLAGS='-D warnings' cargo doc --no-deps --workspace --lib   Finished、警告 0
cargo +1.85 check --workspace --all-targets               Finished
./tools/check_no_std.sh                                   no_std OK
git diff main -- '*.rs' | wc -l                           0
```

README の中のリンク 33 本を `curl -sI -L` で引いて、GitHub と playground の 27 本が 200。
crates.io の 6 本は HTML 側が既定の User-Agent に 403 を返す（bot 避けで、404 ではない）ので、
`https://crates.io/api/v1/crates/<name>` を引いて 200 と `max_version` を確かめた:
`sabiruby` 0.6.0、`sabiruby-cli` 0.6.0、`sabiruby-compiler` 0.3.0、`sabiruby-macros` 0.1.0、
`sabiruby-serde` 0.2.0、`cc` 1.4.7。公開前なので、これが今 crates.io にある版である。

`cargo publish --dry-run` は公開の順序（macros → sabiruby → compiler → serde → cli）で
5 つとも実行した。結果は 7 節。

## 7. dry-run の結果

公開の順序で 5 つとも。`--allow-dirty`（commit 前に回したため）。どれも `Verifying` →
`Uploading` → `aborting upload due to dry run` まで進み、エラーは無い。

```
$ cargo publish --dry-run -p sabiruby-macros
    Packaged 7 files, 23.2KiB (7.7KiB compressed)
   Verifying sabiruby-macros v0.1.1 … Finished
$ cargo publish --dry-run -p sabiruby
    Packaged 158 files, 2.4MiB (767.8KiB compressed)
   Verifying sabiruby v0.6.1 … Finished
$ cargo publish --dry-run -p sabiruby-compiler
    Packaged 94 files, 3.0MiB (405.5KiB compressed)
   Verifying sabiruby-compiler v0.3.1 … Finished
$ cargo publish --dry-run -p sabiruby-serde
    Packaged 11 files, 78.0KiB (21.9KiB compressed)
   Verifying sabiruby-serde v0.2.1 … Finished
$ cargo publish --dry-run -p sabiruby-cli
    Packaged 6 files, 28.0KiB (9.3KiB compressed)
   Verifying sabiruby-cli v0.6.1 … Finished
```

5 節に書いたとおり、compiler・serde・cli の 3 つは **VM を上げる前に**通っている
（`^0.6.0` は crates.io の 0.6.0 で満たされる）。0.6.0 のときと違うのはそこだけで、
本番の順序は変えない: `sabiruby` を先に上げたあとに残りを上げれば、tarball の中の
`Cargo.toml` が名指しする `^0.6.0` は 0.6.1 でも 0.6.0 でも満たされ、どちらでも整合する。

`cargo publish --workspace` は使わない。0.6.0 の worklog §9 の理由（既に公開済みの版を
含む workspace では `already exists` の警告のまま進む）がそのまま当てはまる。

## 8. 気づいた点

1. **`src/lib.rs` の crate ドキュメントに古い数がある。** `src/lib.rs:9` が「its own test suite
   passes 1819 of 1866 assertions」と言っているが、`docs/verification/mrbtest.md:117` は
   2344 of 2507 である。docs.rs の 1 ページ目に出る文なので、crates.io の README と同じ種類の
   古さである。今回は `.rs` に触らない仕事なので直していない。
   **属する先**: VM（docs.rs に出る文面）。
2. **0.6.0 の worklog §10-1 が事実と違う**（4 節）。`CHANGELOG.md` は `861b133` 以来
   package に入っている。worklog は日付つきの記録なので書き換えないが、次に読む人が
   同じ確認を省かないように、ここに書いておく。
   **属する先**: 公開の手順。
3. **README の数を CI が見ていない。** 18 fixtures、112 test files、2344/2507、36 gems は
   どれも repo の中から数え直せるのに、ずれても誰も気づかない（今回 compiler README の
   17/61 がそうだった）。`tools/` に「README の数を数え直して合わなければ落ちる」スクリプトを
   置くことはできる。やるかどうかは著者の判断。
   **属する先**: 検証の仕組み。
4. **rubevy の `description` と README の冒頭**（読むだけ読んだ。別の担当が作業中なので
   触っていない）は 9 節。
   **属する先**: rubevy。

## 公開した（本体、2026-09-22）

`readmes` を main に入れ（その前に本体が `src/lib.rs` の crate ドキュメントの「1819 of 1866」を `docs/verification/mrbtest.md` の
2344 of 2507 に 1 行直した — docs.rs の最初のページに出る文で、この仕事と同じ種類の古さ）、`cargo test --workspace` 250 通過、push（`2e5d95b..479924e`）、
その commit の CI が緑になってから、crate ごとに dry-run → publish:
`sabiruby-macros` 0.1.1 → `sabiruby` 0.6.1 → `sabiruby-compiler` 0.3.1 → `sabiruby-serde` 0.2.1 → `sabiruby-cli` 0.6.1。タグ `v0.6.1`（`479924e`）。
公開後に crates.io の API で 5 つのバージョンと description を確かめた。
