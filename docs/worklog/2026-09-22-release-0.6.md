# 2026-09-22 0.6.0 の準備 — 4 つ出して 1 つ据え置く

ブランチ `release-0.6`（main `3c572a4` から）。作業場所は git の worktree
`kishima/sabiruby-wt-release-0.6`。**publish も tag も実行しない**（著者がやる）。
ここでやったのは「crates.io に 0.6.0 がまだ無い状態で通るところまで通す」ことで、
確認はすべて `--dry-run` までである。先例は
[`2026-09-17-release-0.5.md`](2026-09-17-release-0.5.md)（5 つ全部を初めて出したとき）と
[`2026-09-18-release-0.5.2.md`](2026-09-18-release-0.5.2.md)（変わった 2 つだけを出したとき）。

## 2. 何が変わったかを crate ごとに数える

```
$ git diff --shortstat v0.5.2..HEAD -- src/       2 files changed,   35 insertions(+),  2 deletions(-)
$ git diff --shortstat v0.5.2..HEAD -- serde/     6 files changed, 1008 insertions(+), 11 deletions(-)
$ git diff --shortstat v0.5.2..HEAD -- compiler/  （空）
$ git diff --shortstat v0.5.2..HEAD -- cli/       （空）
$ git diff --shortstat v0.5.2..HEAD -- macros/    （空）
```

動いたのは 2 つだけである。`src/` の 35 行は `src/host_store.rs` の 7 行と `src/vm.rs` の
30 行で、`serde/` の 1008 行はほぼ `declare.rs`（+448）とそのテスト（+379）である。

公開 API の差分は 0.5.0 のときと同じやり方で**両方向から**取った（片方向だと、消えたものと
増えたもののどちらかしか見えない。`2026-09-17-release-0.5.md` の 3 節）。

```
$ git diff v0.5.2..HEAD -- src/ | grep -E "^[-+]\s*(pub|    pub) (fn|const|struct|enum|trait|type|use|mod)"
-    pub fn current_line(&self) -> Option<u32> {
+    pub fn next_line(&self) -> Option<u32> {
+    pub fn backtrace_line(&self) -> Option<u32> {
```

`-` 側に 1 行ある。これが今回の版を決めている。`serde/` の側は `-` 側が 1 行だけで、
しかもそれは「壊れた」ほうではなく**壊れ方が変わった**ほうだった:

```
-    pub fn symbol_keys() -> Options { Options { symbol_keys: true } }
+    pub fn symbol_keys() -> Options { Options { symbol_keys: true, symbol_map_keys: false } }
+    pub fn symbols() -> Options { Options { symbol_keys: true, symbol_map_keys: true } }
+pub mod declare;            （以下 declare の 17 個の pub）
```

`Options` に公開フィールドが 1 つ増えただけなら、それ自体が破壊的変更である（構造体リテラルで
作っていた人が壊れる）。実際に壊れるのはそこではなく `#[non_exhaustive]` が付いたことで、
**この先フィールドが増えても壊れないようにするために、一度だけ壊す**という取引をしている
（`491ec0e`）。grep で確かめた:

```
$ git show v0.5.2:serde/src/lib.rs | grep -n "non_exhaustive\|pub mod"
84:pub mod de;  85:pub mod error;  87:pub mod json;  88:pub mod ser;
$ git show v0.5.2:serde/src/declare.rs
fatal: path 'serde/src/declare.rs' exists on disk, but not in 'v0.5.2'
```

つまり `declare` は 0.1.0 に**入っていない**（指示が確かめろと言っていた点）。公開済みの
0.1.0 に対しては丸ごと新機能で、破壊的なのは `#[non_exhaustive]` と、`expose` が返す Hash の
map のキーが String から Symbol になった振る舞いのほうである。

## 3. 版 — 4 つ上げて 1 つ据え置く

| crate | 前 | 後 | なぜ |
|---|---|---|---|
| `sabiruby` | 0.5.2 | **0.6.0** | `Vm::current_line` を消した（`5b4c0a5`）。`next_line`・`backtrace_line` の追加（`cd013fa`・`d0bbde0`）も入る |
| `sabiruby-serde` | 0.1.0 | **0.2.0** | `Options` が `#[non_exhaustive]`（`491ec0e`）。`declare`（`2f1043f`・`c38f0e2`・`d0bbde0`）、`expose` の map のキー |
| `sabiruby-compiler` | 0.2.3 | **0.3.0** | 中身は 1 バイトも動いていない。`sabiruby` への要求を 0.6 にするための republish、ただし 0.2.4 ではない（下記） |
| `sabiruby-cli` | 0.5.0 | **0.6.0** | 中身は動いていない。release の名前（＝ VM の版）に合わせる。両方を名指ししている |
| `sabiruby-macros` | 0.1.0 | 0.1.0 | **出さない**（下記） |

### `sabiruby-compiler` が 0.2.4 ではなく 0.3.0 である理由

0.5.0 のとき compiler は 0.2.1 → 0.2.2 だった。あのときも中身は動いておらず、`sabiruby` への
要求を 0.4.0 → 0.5.0 にするためだけの republish だった。同じ形なら今回も 0.2.4 でよさそうに
見える。**そうしなかったのは、この crate の公開 API に `sabiruby` の型が出ているから**である。
`compiler/src/lib.rs` を読むと feature `host` の裏に

```rust
impl sabiruby::Host for Compiler {
    fn compile(&mut self, src: &[u8], opts: &sabiruby::EvalOptions) -> Result<Vec<u8>, String> {
```

があり、`sabiruby::Host` も `sabiruby::EvalOptions` も**利用者から見える型**である。
つまり `sabiruby` はこの crate の *public dependency* で、その major（`0.x` では minor）を
上げるのは、この crate 自身にとっての破壊的変更になる。具体的にどう壊れるかを書くと:

* `sabiruby = "0.5"` と `sabiruby-compiler = { version = "0.2", features = ["host"] }` を
  書いているプログラムがある。
* compiler を 0.2.4 として出すと、そのプログラムの `cargo update` が 0.2.4 を選ぶ。
  `^0.2` は 0.2.4 を受けるからである。
* 0.2.4 は `sabiruby ^0.6` を要求するので、そのプログラムには VM が 2 つ入る。
  `Compiler` が実装しているのは 0.6 の `Host` で、プログラムが渡したいのは 0.5 の `Vm` である。
  **コンパイルが通らなくなる。**
* 0.3.0 として出せば `^0.2` は 0.3.0 を受けないので、そのプログラムは今までどおり 0.2.3 の
  ままでいられる。

`0.x` の caret は minor を major として読むので、「これは新しい VM を要る版だ」と言える
唯一の場所が minor である。`docs/design/compiler.md` の "Publishing" にこの段落を足した。

### `sabiruby-macros` を出さない理由

`v0.5.1` から 1 行も変わっておらず、しかも**この crate は `sabiruby` に依存していない**。
生成するコードが `::sabiruby::…` を絶対パスで名指しするので（`2026-09-17-release-0.5.md` の
1 節）、VM が 0.6 になっても macros のマニフェストは 1 文字も変わらない。dev-dependency の
`sabiruby` は path だけで版が無く、packaging で落ちる。**0.6 に縛られているものが 1 つも無い**
ので、公開済みの 0.1.0 がそのまま最新でよい。指示の「中身が変わっておらず `sabiruby` にも
依らない crate は出さない」はこれ 1 つに当たる。

## 6. 順序と `--dry-run`

依存の向きは 0.5.0 のときと同じである。VM が `sabiruby-macros` を optional に持っている
以上 VM は最初ではなく、compiler の VM への依存も optional なので VM は compiler より前。

```
sabiruby-macros 0.1.0（出さない）→ sabiruby 0.6.0 → sabiruby-compiler 0.3.0
                                    → sabiruby-serde 0.2.0 → sabiruby-cli 0.6.0
```

これは推測ではなく `cargo publish --dry-run --workspace` のログの `Uploading` 行の順である。
compiler と serde の間は互いに依存が無いので、その 2 つの順は自由。cli は両方の後。

| コマンド | 結果 | 理由 |
|---|---|---|
| `cargo publish --dry-run -p sabiruby` | **通る** | 依存は公開済みの `sabiruby-macros` 0.1.0 だけ。157 files, 2.4MiB (約 760KiB compressed) |
| `cargo publish --dry-run -p sabiruby-macros` | 通る（出さない） | `warning: crate sabiruby-macros@0.1.0 already exists on crates.io index`。7 files, 22.8KiB (7.5KiB) |
| `cargo publish --dry-run -p sabiruby-compiler` | **落ちる** | `sabiruby ^0.6.0` が crates.io に無い |
| `cargo publish --dry-run -p sabiruby-serde` | **落ちる** | `sabiruby ^0.6` が crates.io に無い |
| `cargo publish --dry-run -p sabiruby-cli` | **落ちる** | `sabiruby ^0.6.0` が crates.io に無い |
| `cargo publish --dry-run --workspace` | **通る** | 5 つとも package・verify・（打ち切られた）upload まで |

落ちた 3 本は 0.5.0 のときと**同じ 1 種類の理由**で、それ以外の理由で落ちたものは無い:

```
error: failed to prepare local package for uploading
Caused by:
  failed to select a version for the requirement `sabiruby = "^0.6.0"`
  candidate versions found which didn't match: 0.5.2, 0.5.1, 0.5.0, ...
  location searched: crates.io index
  required by package `sabiruby-compiler v0.3.0 (…/compiler)`
```

**VM を publish した後でないと dry-run が通らないのはこの 3 つ**（compiler・serde・cli）で、
本体は publish の途中でこの 3 本を回すことになる。9 節のコマンドの列にそう並べた。

`--workspace` が通るのは、まだ公開されていない依存を workspace 自身の `.crate`
（`target/package/tmp-registry`）から解決するためで、ログに
`Unpacking sabiruby v0.6.0 (registry …/tmp-registry)` と
`Unpacking sabiruby-compiler v0.3.0 (…)` の 2 行が出る。cargo は 1.97.0。

package に入るファイルと大きさ（`--workspace` の 1 回から）:

| crate | files | 生 | 圧縮後 |
|---|---:|---:|---:|
| `sabiruby-macros` 0.1.0 | 7 | 22.8KiB | 7.5KiB |
| `sabiruby` 0.6.0 | 157 | 2.4MiB | 約 760KiB |
| `sabiruby-compiler` 0.3.0 | 94 | 3.0MiB | 405.4KiB |
| `sabiruby-cli` 0.6.0 | 6 | 27.5KiB | 9.2KiB |
| `sabiruby-serde` 0.2.0 | 11 | 77.2KiB | 21.7KiB |

VM は 0.5.2 の 151 files / 2.3MiB (709.9KiB) から 157 files / 2.4MiB に増えた。増えた
6 ファイルは `include` が拾う `docs/**/*.md` の新しい分（**この worklog 自身を含む**）で、
`src/` は 2 ファイルしか動いていない。版だけを上げた commit の時点では 156 files /
753.0KiB、この worklog を足して 157 files / 760.5KiB。圧縮後の端数はこの文を書き直すたびに
動くので、ここでは「約 760KiB」と書く——`include` が `/docs/**/*.md` を拾う以上、
記録そのものが package の一部である。compiler は 0.5.2 のとき（94 files, 3.0MiB, 405.4KiB）と**1 バイトも
同じ**で、中身が動いていないことがここにも出ている。

dry-run の警告は「`tests/*.rs` が package に入っていないのでテストを無視する」だけで、
以前の公開と同じ。ほかの警告は macros の `already exists on crates.io index` の 1 行。

## 8. 使う側 — 3 つとも、どの repo にも書かずにコピーで建てた

スクラッチパッドに `git archive HEAD` で展開したコピーを作り、そちらだけを書き換えた。
`CARGO_TARGET_DIR` もスクラッチパッドで、どの repo の `target/` にも触っていない。

### sabiruby-playground — 直すところは無い

`wasm/Cargo.toml` が `path = "../../sabiruby"` で隣を見ているだけで、**版の要求が 1 つも
無い**。`pg/sabiruby` をこの worktree への symlink、`pg/sabiruby-playground` を main の
`git archive` から展開したコピーにして `wasm/` で `cargo check`。

```
$ CC_wasm32_wasip1=~/.local/wasi-sdk-34.0-x86_64-linux/bin/clang \
  AR_wasm32_wasip1=~/.local/wasi-sdk-34.0-x86_64-linux/bin/llvm-ar cargo check
    Updating sabiruby v0.5.2 (…/pg/sabiruby) -> v0.6.0
    Updating sabiruby-compiler v0.2.3 (…/pg/sabiruby/compiler) -> v0.3.0
    Finished `dev` profile … in 3.89s
```

`wasm/.cargo/config.toml` が `target = "wasm32-wasip1"` を立てているので wasi-sdk が要る
（`2026-09-21-serde-lines.md` §7.6 の気づいた点 2 と同じ）。公開後に playground が要るのは
`SABIRUBY_REF` を 0.6.0 の commit に上げることだけで、それは commit の話であって版の話では
ない。

`sabiruby-compiler` と `sabiruby-serde` も版で名指ししていて、**それも一緒に上げないと
games の `[patch.crates-io]` が効かない**（次の節）。

| `[dev-dependencies]` | `sabiruby-compiler = { version = "0.2.2", features = ["host"] }` | `version = "0.3"` |
| `[dev-dependencies]` | `sabiruby = { version = "0.5.1", features = ["macros"] }` | `version = "0.6"` |

コピーに `.cargo/config.toml` を置いて 3 つをこの worktree に向け（rubevy の `Cargo.toml`

`rubevy-build` は SabiRuby を名指ししていないので、その版は動かない。

1.85 のままなので数は変わらない（文面の `0.5.x` は著者が直すかどうか決める話として残した）。

### rubevy_games — 3 行と、rubevy の git の rev

| 行 | 前 | 後 |
|---|---|---|
| `[workspace.dependencies]` | `sabiruby = "0.5.1"` | `sabiruby = "0.6"` |
| `[workspace.dependencies]` | `sabiruby-compiler = { version = "0.2.3", features = ["host"] }` | `version = "0.3"` |
| `[workspace.dependencies]` | `sabiruby-serde = "0.1.0"` | `sabiruby-serde = "0.2"` |
| `Cargo.lock` | rubevy の rev（今 `abfc875`） | `cargo update -p rubevy`（rubevy を push した後） |

`[patch.crates-io]` の 3 行は git のままでよい。コピーではそこをこの worktree の path に
向け、`rubevy` / `rubevy-build` をコピーの path に向けて
`cargo check --workspace --all-targets` を通した。

**§7.6 が警告していたことを実際に踏んで確かめた。** 版を上げずに patch だけを新しい VM に
向けるとどうなるかを、もう 1 つのコピーで `cargo metadata` に解かせた（コンパイルまで
行かなくても resolver の答えで分かる）:

```
warning: patch `sabiruby-compiler v0.3.0 (…)` was not used in the crate graph
warning: patch `sabiruby-serde v0.2.0 (…)` was not used in the crate graph
      Adding sabiruby v0.5.2 (available: v0.6.0)
      Adding sabiruby-compiler v0.2.3 (available: v0.3.0)
      Adding sabiruby-serde v0.1.0 (available: v0.2.0)

$ （metadata の packages から sabiruby* を抜いたもの）
sabiruby 0.5.2 registry+https://github.com/rust-lang/crates.io-index
sabiruby 0.6.0 local/patched
sabiruby-compiler 0.2.3 registry+…
sabiruby-serde 0.1.0 registry+…
```

**1 つのグラフに `sabiruby` が 2 つ入っている。** compiler と serde は patch が
「使われなかった」と警告が出るだけで済むが、VM のほうは警告が出ない——rubevy（版を上げた
コピー）の `^0.6` は patch で満たされ、games 自身の `^0.5.1` は crates.io の 0.5.2 で
満たされるので、**cargo から見ればどちらも解けている**。`Value` が別物になるのは
ビルドしてからしか分からない。`cargo check` が通らなくなるのではなく、
**警告 3 行のまま 2 つ目の VM が入る**というのが、この失敗の一番いやなところである。

だから順番は **rubevy を先に直して push → games が 3 行を上げて `cargo update -p rubevy`**
になる。games が先だと、rubevy が `^0.5.1` を名指ししている間は patch が効かない。

## 9. 本体が打つコマンド

作業ツリーが clean で、`main` が `origin/main` と同じ位置であることを確かめてから。
`cargo publish --workspace` を**使わない**のは、それが `sabiruby-macros` 0.1.0 も
出そうとするからである（dry-run では `already exists` の警告のまま `Uploading` まで進む）。

```
# 1. release-0.6 を main に入れて push（タグを打つ commit を決める）
git checkout main && git merge --no-ff release-0.6 && git push origin main

# 2. VM。ここが通るまで残り 3 つは dry-run すら通らない
cargo publish --dry-run -p sabiruby        # 通ることは確認済み
cargo publish -p sabiruby                  # -> sabiruby 0.6.0

# 3. VM が index に出てから、残り 3 つ。dry-run はここで初めて通る
cargo publish --dry-run -p sabiruby-compiler
cargo publish -p sabiruby-compiler         # -> sabiruby-compiler 0.3.0
cargo publish --dry-run -p sabiruby-serde
cargo publish -p sabiruby-serde            # -> sabiruby-serde 0.2.0
cargo publish --dry-run -p sabiruby-cli    # compiler 0.3.0 も index に要る
cargo publish -p sabiruby-cli              # -> sabiruby-cli 0.6.0

# 4. タグ。名前は release（= VM の版）、ほかの 3 つはメッセージに
git tag -a v0.6.0 -m "SabiRuby 0.6.0: Vm::current_line removed for next_line and backtrace_line; sabiruby-serde 0.2.0 (declare, Options non_exhaustive), sabiruby-compiler 0.3.0, sabiruby-cli 0.6.0" <main の commit>
git push origin v0.6.0
```

`sabiruby-macros` は打たない。タグの打ち方は `v0.5.0`・`v0.5.1`・`v0.5.2` と同じ注釈付きで、
compiler と serde の版はタグの名前に出ないのでメッセージに書く（`2026-09-18-release-0.5.2.md`
の 3 節と同じ）。

公開の後、使う側は

```
# rubevy（先）: 上の 8 節の 5 行を直して push
# rubevy_games（後）: 3 行を直し、rubevy の rev を上げる
cargo update -p rubevy -p rubevy-build
# sabiruby-playground: .github/workflows/pages.yml の SABIRUBY_REF を 0.6.0 の commit に
```

## 10. 残っていること・気づいた点

1. **`CHANGELOG.md` は今も `include` に入っていない。** root crate の `include` は
   `/src`・`/build.rs`・`/docs/**/*.md`・`/README.md`・2 つの LICENSE で、crates.io の
   ページから CHANGELOG は読めない。`2026-09-17-release-0.5.md` の 6 節が同じことを
   著者判断として残しており、今回も触っていない。0.6.0 は破壊的変更のある版なので、
   「Coming from 0.5.2」が crates.io から読めないのは 0.5.2 のときより惜しい。
   **属する先**: 公開の設定（報告のみ）。
2. **`rubevy` の `rust-version` のコメントが「sabiruby 0.5.x says 1.85」と言っている。**
   0.6.0 も `rust-version = "1.85"` なので数は変わらないが、文面は古くなる。
   rubevy の版を上げるときに一緒に直すかどうかは著者の判断。
   **属する先**: rubevy（報告のみ、直していない）。
3. **`docs/design/utf8.md` の依存の例が 0.3.0 の時点から古かった。** 「今」を言う design の
   文書に版が直に書いてあると、release のたびに拾わないと静かに古くなる。README の
   "Usage" と `docs/design/macros.md` と 3 か所あり、今回は全部直したが、
   **次に拾い漏らす場所**でもある。1 か所にまとめるか、caret を `"0"` のように書いて
   版を書かない形にするかは著者の判断。
   **属する先**: docs の書き方（報告のみ）。
4. **`cargo publish --workspace` は「もう公開済みの crate」を含む workspace では使えない。**
   dry-run は `already exists on crates.io index` の警告を出したうえで `Uploading` まで
   進むので、dry-run が通ったからといって本番が通るとは限らない。9 節で 1 つずつ打つ形に
   したのはそのためで、0.5.0 のとき「1 コマンドでよい」と書いた結論は、
   **5 つ全部が未公開だったから**成り立っていた。
   **属する先**: 公開の手順（`docs/design/compiler.md` に足すかどうかは著者の判断）。
