# 2026-09-17 0.5.0 の準備

ブランチ `release-0.5`（main `1c747bf` から）。作業場所は git の worktree `kishima/sabiruby-wt-rel`。
同じ日の `2026-09-17-release-prep.md` は「出荷するビルドをどう作るか」（`codegen-units = 1`）の記録で、
こちらは「何を、どの版で、どういう依存関係で出すか」の記録である。**publish も tag も実行しない**。
確認はすべて `--dry-run` まで。

## 1. `sabiruby` の feature `macros`

### 決まっていたこと

著者判断（2026-09-17）は「serde / serde_derive と同じ形にする」。つまり利用者が書くのは

```toml
sabiruby = { version = "0.5", features = ["macros"] }
```

の 1 行と `use sabiruby::{RubyClass, ruby_methods};` の 1 行だけで、`sabiruby-macros` を
`Cargo.toml` に書かせない。

### 名前が衝突しないのはなぜか

ここが一番先に確かめるべきところだった。`src/lib.rs` には既に

```rust
pub use host_store::{HostStore, RubyClass};
```

があり、**`RubyClass` という名前は既に埋まっている**（trait のほう）。そこへ
`pub use sabiruby_macros::RubyClass;`（derive マクロ）を足す。Rust の名前空間は型・値・マクロの 3 つに
分かれていて、trait は型名前空間、derive マクロはマクロ名前空間にいるので、同じ名前で共存できる。
しかも `use sabiruby::RubyClass;` は**両方を一度に**持ってくる。serde の `use serde::Serialize;` が
trait と derive を同時に入れているのと同じ仕掛けで、この重なりは事故ではなく設計のほうである
——derive が実装する trait と derive が同じ名前を持つのは利用者にとって都合がよい。
`macros/tests/reexport.rs` の 2 本目のテストは、そのことを明示的に確かめる（`use` は 1 行なのに、
`Counter::borrow`（trait のメソッド）が呼べる）。

### マクロが吐くパスは既に絶対だった

指示は「生成コードが `sabiruby` をスコープ頼みで呼んでいたら直せ」だった。読んだのは
`macros/src/expand.rs` で、`::sabiruby::` が 20 箇所、スコープ頼みの `sabiruby::` は 0 箇所。
`grep -c "::sabiruby" macros/src/expand.rs` が 20、`grep -n "[^:]sabiruby::"` が空。
つまり**直すところは無かった**。これは偶然ではなく、`macros/src/lib.rs` の crate doc に
「この crate は `sabiruby` に依存しない: 生成物は `::sabiruby::…` を名指しする」と最初から書いてある
（`33fa232`、stage 6a）。再エクスポート越しでも直接依存でも同じコードに展開される、という保証が
そこから来ている。文書の言い方だけ「absolutely（絶対パスで）」と補って、なぜそれが効くのかを
`docs/design/macros.md` の新しい節「How a host depends on it」に書いた。

### dev-dependency の循環

`sabiruby`（feature `macros`）→ `sabiruby-macros` → dev → `sabiruby`（feature `macros`）という輪になる。
cargo はこれを通す。dev-dependency は「その crate のテストを建てるときだけ」必要で、
`sabiruby-macros` の **lib** を建てるのに `sabiruby` は要らないので、ユニットの水準では輪になっていない。
publish 側も安全で、`macros/Cargo.toml` の dev-dependency は path だけ・version 無しなので、
crates.io に渡るマニフェストからは剥がれる（`54c51a6` が compiler の dev-dependency で同じことをしている）。

テストの置き場所は迷った。指示は「`macros/tests/` に 1 本、または root crate の
`tests/macros_reexport.rs` を `#[cfg(feature = "macros")]` の裏に」だった。**後者を採らなかった**のは、
`macros` が既定オフである以上、`cargo test --workspace` でそのファイルは丸ごと消えて、CI が一度も
通らないテストになるからである。feature の統合（同じ workspace 内で誰かが `macros` を要求すれば
`sabiruby` は feature 込みで建つ）に賭ければ動くが、それは resolver の挙動に寄りかかった書き方で、
「このテストは走るのか」が読んで分からない。`macros/tests/reexport.rs` に置き、
`macros/Cargo.toml` の dev-dependency を `features = ["macros"]` にすると、`cargo test --workspace` が
何もしなくても必ず走る。`player.rs`（直接依存側）と `reexport.rs`（feature 側）が対になって、
「2 通りの書き方が同じものに展開される」ことを言う。

### rustdoc で 2 回転んだ

1 回目: crate doc に `[`RubyClass`](macro@RubyClass)` と書いたら、**feature を切ったビルドで**
`unresolved link` になった。当然で、feature オフのときマクロは存在しない。crate doc は feature の
有無に関わらず出るので、ここはリンクにせず素のコードスパンにした。`-D warnings` で
`cargo doc --no-deps --workspace --lib` を回して 0 警告、`--features macros` でも 0 警告。

2 回目: 最初 `pub use sabiruby_macros::{RubyClass, ruby_methods};` の 1 文に doc コメントを付けたところ、
同じ doctest が 3 つに複製された（`src/lib.rs - (line 124)`、`- RubyClass (line 124)`、
`- ruby_methods (line 124)`）。`use` 1 文が複数の item を持ち込むと doc がそれぞれに付くためである。
`pub use` を 2 文に割り、例は derive のほうにだけ置いた。ついでに、例を `ignore` ではなく
**本物の doctest** にできることに気づいた（`sabiruby` の doctest は `sabiruby` を extern crate として
リンクするので、feature が入っていればマクロも見える）。`cargo test -p sabiruby --features macros --doc`
で 14 本通過、うち 1 本がこの例である。`ignore` のままなら「書いてあるが誰も確かめていない例」だった。

### no_std

`tools/check_no_std.sh` を 5 通り回した（CI が回すのは `--features regexp` と `--features utf8` の 2 つ。
引数なしを足して 3 通り、さらに `macros` 入りの 2 通り）。全部 `no_std OK`。
proc macro はホスト向けにコンパイルされてコンパイル時に走るだけなので、`thumbv7em-none-eabi` の
ライブラリには 1 バイトも入らない——というのは理屈で、実際に建つことを確かめたのがこの 5 回である。

| 組合せ | 結果 |
|---|---|
| （既定なし） | no_std OK |
| `--features regexp` | no_std OK |
| `--features utf8` | no_std OK |
| `--features macros` | no_std OK |
| `--features "utf8 regexp macros"` | no_std OK |

## 2. 版

| crate | 前 | 後 | なぜ |
|---|---|---|---|
| `sabiruby` | 0.4.0 | **0.5.0** | 著者判断。ホスト橋・スケジューラ・gem・性能の 4 方面が動き、破壊的変更がある |
| `sabiruby-cli` | 0.4.1 | **0.5.0** | 同上。VM に合わせる |
| `sabiruby-compiler` | 0.2.1 | **0.2.2** | 下記 |
| `sabiruby-macros` | 0.1.0 | 0.1.0 | 生成するコードは変わっていない（変えたのは呼ばれ方だけ）。初公開 |
| `sabiruby-serde` | 0.1.0 | 0.1.0 | 初公開 |

### `sabiruby-compiler` を上げるかどうか

指示は「公開済みの 0.2.1 から変わっていれば上げる」だった。0.2.1 を決めたのは `a82f163`
（`git log --oneline -S'version = "0.2.1"' -- compiler/Cargo.toml`。tag は `v0.1.0` と `v0.2.0` しか
無いので、tag ではなく版を書いた commit のほうから探した）。そこから HEAD までの `compiler/` の差分は

```
compiler/Cargo.toml       | 2 +-   repository = kishima/sabiruby → sabiruby/sabiruby
compiler/vendor/VENDOR.md | 2 +-   docs/eval-require-plan.md → docs/plans/eval-require-plan.md
```

の 2 行だけで、**vendor した本家のコードも C の shim も 1 バイトも動いていない**。これだけなら
上げなくてよさそうに見えるが、上げる理由は別にある。`compiler` の `sabiruby` への依存
（optional、feature `host`）が `0.4.0` を名指ししているので、これを `0.5.0` に変えないと、
`sabiruby-cli` が VM を 0.5、compiler 経由の VM を 0.4 として**同じプログラムに 2 つの `sabiruby`**
を引き込む。型が別物になって `Compiler` が `sabiruby::Host` を実装していないと言われる。
版を動かさずに依存だけ書き換えることはできない（公開済みの 0.2.1 は不変）ので、0.2.2 になる。
つまり中身の変化ではなく**依存の付け替えのための republish** で、`docs/design/compiler.md` に
その旨を 1 段落書いた。

### path と version の両方を書く、ただし dev-dependency は別

通常の依存は全部 `path` と `version` の両方を持つようにした:

* `sabiruby` → `sabiruby-macros` `{ version = "0.1.0", path = "macros", optional = true }`
* `sabiruby-compiler` → `sabiruby` `0.5.0`
* `sabiruby-cli` → `sabiruby` `0.5.0`、`sabiruby-compiler` `0.2.2`
* `sabiruby-serde` → `sabiruby` `0.5`

**dev-dependency は意図的に path だけのまま残した。** ここは指示の「すべての workspace 内の依存は
path と version の両方を持つ」と食い違うので、理由を書く。`sabiruby` の dev-dependency は
`sabiruby-compiler`、`sabiruby-macros` の dev-dependency は `sabiruby` で、どちらも version を書くと
crates.io から解決されるようになり、**公開の順序に輪ができる**（`sabiruby` を出すには
`sabiruby-compiler` が要り、それを出すには `sabiruby` が要る）。version の無い path 依存は
公開時にマニフェストから落ちるので輪にならない。これは `54c51a6`
（"dev-dependency on the compiler: path only, no version"）で一度決まっていることで、
`docs/design/compiler.md` の最後の段落がその判断を記録している。今回もそれに従った。

## 3. `CHANGELOG.md`

repo にはこれまで CHANGELOG が無かった。0.4.0 が何だったかを言っている場所を探すと、
`docs/design/compiler.md` の "Publishing" 節（版と、0.3.0 と 0.4.0 が何を足したか）と、
版を上げた commit のメッセージ（`a82f163`、`1fe5f9d`）の 2 つしか無い。README の "Status" は
現在の状態であって差分ではない。そこで CHANGELOG は、0.5.0 を厚く、0.1.0〜0.4.0 は
その 2 つの出典から薄く書いた。

**指示の「すべての主張は commit か doc に辿れること」を、機械的に守った。** 各項目に commit の
短縮 SHA を書き、性能の数字は `docs/verification/bench.md` から取り、書く前に必ず元を読んだ。
その結果、書きながら**既存の文書の誤りが 1 つ見つかった**。

### 見つけた誤り: `hash_keys` は 0.4.0 のものではない

`docs/design/compiler.md` の "Publishing" 節は、0.4.0 が足したものとして
`task_next_wakeup_ticks`、`task_pending`、`task_queue_new` / `task_queue_push` /
**`task_queue_len` / `task_queue_try_pop`**、**`Vm::hash_keys`**、`VERSION`、`REVISION` を挙げていた。
ところが `git log --oneline -S"fn hash_keys" -- src/ | tail -1` は `6af8276`
（"host api: hash_keys, task_queue_len and task_queue_try_pop"）を答える。3 つとも同じ commit で、
これは `a82f163`（0.4.0）より**後**である。版を上げた commit `a82f163` 自身のメッセージは正しく、
`task_next_wakeup_ticks`、`task_pending`、`task_queue_new` / `task_queue_push`、`VERSION`、
`REVISION` しか挙げていない。あとから "Publishing" 節を書いた人（あるいはセッション）が、
0.4.0 と 0.5.0 の作業を混ぜたらしい。compiler.md を直し、CHANGELOG の 0.4.0 の項にも
「ここは以前こう書かれていたが違う」と 1 段落残した。消すのではなく残したのは、
古い commit や rubevy 側の記述がその誤った版の話を引いている可能性があるためである。

### 破壊的変更をどう探したか

commit メッセージを 1 つずつ読むほかに、**公開 API の署名を機械的に差分した**:

```
git diff a82f163..HEAD -- src/ | grep -E "^[-+]\s*(pub|    pub) (fn|const|struct|enum|trait|type|use)"
```

`-` 側に出たのは 5 行だけで、そのうち実質は `Vm::array` と `Vm::ary` が
`Option<&Vec<Slot>>` → `Option<&[Slot]>` に変わった 2 つ（`35d58a5` の `ArrayData` に start offset が
入って `shift` が O(1) になった副作用で、配列の中身がそのまま 1 本の `Vec` ではなくなった）。
これは commit メッセージのどこにも「破壊的」と書かれておらず、**署名の差分でしか見つからない**種類の
変更だった。逆に `Method` に `Closure` variant が増えた件（`93824b1`）は `+` 側にしか出ないので、
今度は commit メッセージのほうから拾った。`Method` は `pub` で `#[non_exhaustive]` が付いていない
（`grep -rn non_exhaustive src/` が空）ので、crate の外の網羅 `match` は壊れる。
**両方向から探さないと片方しか見つからない**、というのがこの作業で分かったことである。

最終的に 10 項目。Rust の API が変わるもの（`register` の戻り値、op カウント既定オフ、
`array`/`ary` の型、`Method::Closure`、compiler の依存）と、Ruby から見える振る舞いが変わるもの
（`default-features = false` に `Regexp` が無い、`Hash#default=` と `default_proc=` が互いを消す、
空のキーワード Hash が届く、`singleton_method_added` が `BasicObject` へ、`allocate` した
オブジェクトのメッセージ、`method_missing`／添字演算子がネイティブ境界でなくなった）に分かれる。
最後のものは「直った」話でもあるが、`Fiber.yield` が例外になることに頼っていたコードは動きが変わるので
破壊的変更のほうに入れた。

### 性能の数字をそのまま引かなかったところ

指示は「4.32x → 2.57x on 27 benchmarks」だった。`bench.md` を読むと**両端でベンチの本数が違う**。
4.32x は最初の基準 `e9da768` の「all」で、そのとき集合は 20 本
（`vm_optimization_bench` はまだ 5 本に割られておらず、`bm_ao_render` と `bm_mandel_term` は
`printf` が無くて走らなかった）。2.57x は `96221fb` の 27 本。`bench.md` はこの食い違いを知っていて、
段階ごとに「25 shared」と「27 all」の 2 列を出している。CHANGELOG には「4.32x（20 本の基準）→
2.57x（27 本）」と本数を明記し、集合が違うことと bench.md に両方の列があることを 1 文添えた。
数字を丸めて 1 行にすると嘘になる類の話である。
