## 1 回目（`dd8d343`）: 小さなスケジューラが遅い

タスクのマイクロベンチ（2 巡）で、小さい場合が軒並み遅くなっていた: `t_sleep_10` +31.2%、`t_sleep_100` +23.8%、
`t_list_stat` +28.7%、`t_pass_prio` +14.4%、`t_pingpong` +10.4%。大きい場合は速い（`t_sleep_1000` −50%、`t_spawn_join` −95%）。
本体の言う「小さい場合は線を超えて遅くしない」に当たる。命令数は同じなので、スケジューラ自身の仕事が増えている。

原因と直し（`d0d0c8d`）:

1. **`BTreeMap` の定数**。数本のタスクでも、挿入・削除・先頭のたびに木を下りる。鍵はほとんど後ろに付き（通し番号が
   増えるだけ）、出ていくのは先頭なので、**整列した `VecDeque`**（`src/sorted_deque.rs`）に替えた。両端は O(1)、それ以外は
   二分探索で場所を探し、短い側をずらす。`t_sleep_*` と `t_list_stat` はこれで大きく戻った（試しに建てたもので
   `t_sleep_10` 433 → 341 ms、`t_sleep_100` 515 → 347 ms）。途中の要素を抜くと O(n) のずらしになるが、段階 B の
   「1 つずつ見て歩く」数（`TaskState::walked`、`tests/task_scale.rs`）は変わらない。
2. **1 回の入れ直しでタスクを 4 回読み書きしていた**（`q_delete` で 1 回、状態を書いて 1 回、`q_insert` で読んで書いて 2 回）。
   `requeue` にまとめて 2 回にした。
3. **プッシュのたびに `Vec` を作っていた**（`waiting_for` が「最初の 1 本」でも集めて返す）。1 本を起こすときは集めずに探す。
4. `wake_sleepers` の作業用 `Vec` を毎回作らず `TaskState::due` に取っておく。`Task.list` は大きさを先に取る。

`cargo test --release --workspace`（mrbtest の 108 ファイルを含む）、`tests/task_scale.rs`・`task.rs`・`wait_anywhere.rs` を
`SABIRUBY_GC_STRESS=1` でも、`check_no_std` を通した。

### どこから来たか: 段階 B の取り込み（`3e6238c`）で出る

  まわりの置き場所か、`Vm` の並びに乗った何かと見ている。次に試すなら、段階 B の 3 つ（S4・S5・S6）を 1 つずつ外した木を
  建てて同じ 7 本で比べる。

## 続き（本体の指示、同じ日）: 2 つとも直す — 時間を測らずにできる分

著者の規則は「通常時の性能の劣化なし」なので、上の 2 つ（小さい N の +3〜6%、段階 B 以降のタスクを使わない道の遅さ）は
受け入れずに直す。PC が空くまで時間は測らない。建てる・テストする・構造で調べる、までをやった。

### 段階 B の遅さ: 構造で調べたこと

- **関数の大きさ**（`nm -S`）。熱い道で段階 B の前後で変わったのは `op_send_vis` 7500 → 7607 バイトと `call_closure_direct`
  655 → 720 バイトだけ（S5 がネイティブの呼び出しに `mid` と `if r.is_err()` を足した分。`call_native_direct` は
  `op_send_vis` に展開されている）。`exec_frames` は 52557 → 52564、`unwind_return`・`prepare_call`・`call_proc_inner` は同じ。
  `op_send_vis` の逆アセンブルの差は、レジスタの割り当ての入れ替わりと 9 命令。
- **`Vm` の並び**（`offset_of!`、一時的なテストで）。`Vm` は 2456 → 2632 バイト、`TaskState` 272 → 424、`TaskData` 72 → 152
  （`CallInfo` 56・`Context` 104 は同じ）。命令ごとに読むフィールド（`task.running`・`task.switching`・`step_left`・
  `heap`・`stack`・`ci`・`ireps`）はどれも 152 バイト後ろにずれた。**変更前に 128 バイトの空きを足した試し（`pad`）は、
  これとほぼ同じずれを起こして時間が動かなかった**ので、`Vm` の並びは候補から外れる。
- **関数の置き場所**。`exec_frames` の先頭の 64 バイト境界からの位置: 変更前 16、段階 A の終わり 0、段階 B の取り込み 48、
  `dd8d343` 32、`d0d0c8d` 48。段階 B は `BTreeMap` のコード（約 30 kB）を足し、S4・S5 も関数を足したので、後ろの関数の番地が
  全部ずれた。`pad` の試しは番地が変更前と 1 バイトも違わなかった（データだけ変わった）ので、置き場所は試せていない。
- **`ObjId: Ord`** は派生を足しただけで、比較の場所以外のコードは変わらない。`load_ireps` と `irep_gone` は `run_irep` 1 回に
  1 度で、ベンチの中の熱い道ではない。`#[inline]` の付け外しは段階 B に無い。
- **見立て**: 熱い道のコードは S5 の 100 バイトほどしか変わっておらず、その「エラーのときだけ」の部分を外へ出しても変わらなかった
  （`x` の試し）。残るのは置き場所。下の建てたもので確かめる。

## 決めたこと

- **待ちの索引（`sleepers`・`waiters`）は、待ちの列が `TaskState::index_from` 本に届いてから作る**（`6bf9450`）。それまでは
  起こすときに待ちの列を歩く（0.7.0 より前と同じ）。届いたら列の順に索引を作り、列が空になったら捨てる。
  `Vm::task_set_index_from` で変えられる。本体の指示（「実際に要る場合だけ索引を作る」）と著者の規則（通常時の劣化なし）に
  従った選択。**既定は今は 0（最初から索引を作る = 段階 B の振る舞い）**。歩くのと索引の損益分岐は時間を測って決める
  （`ix-head` と `ix-walk` の比較）。測ってもいない数を既定にしないため。
- `tests/task_scale.rs` の順のテスト 7 本は、索引あり（0）と索引なし（`usize::MAX`）の両方で走らせる。全テストを
  既定「索引なし」でも一度通した（コミットはしていない）。
- **小さい N の残り（`t_pass_prio` +5.9%）は、待ちの索引を使わない**（全員 ready で `Task.pass` するだけ）。
  ここに効くのは ready の列と `TaskData` の大きさ（72 → 152 バイト）と置き場所で、索引を遅らせても変わらない見込み。
  上の測定で置き場所かどうかを先に確かめる。
