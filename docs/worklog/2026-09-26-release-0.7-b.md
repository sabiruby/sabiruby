## 決めたこと

計画書に無い分かれ道を、原則で決めたもの。1 行ずつ。

- S5: ネイティブを見つける場所は 3 つにした（SEND が呼んだネイティブが例外を返したとき、`Cci::Skip` のフレームの下、ネイティブのループのフレーム）。ネイティブがネイティブを `funcall` で呼んだ分は数えない — 名前を積む表を呼び出しのたびに持つと、例外の無い普通の呼び出しに費用が乗るから（通常時の性能を落とさない、が 0.7.0 の条件）。
- S5: 本家がフレームを書き換えて名前を運ぶ場所（`instance_exec`、`eval`、`Class.new { }` など）は揃えない。揃えるには `CallInfo` に 1 つ足すか `Cci` を増やすことになり、フレームの形に触る。違いは `tests/custom/native_backtrace.rb` と `docs/design/gems.md` に書いた。
- S5: ネイティブの下にデバッグ情報のあるフレームが 1 つも無いときは本家どおり `(unknown):0` を出す（今までは何も出さなかった）。`caller` の数え方もこれで本家と同じになる。
- S6: `TaskState::queues` の型を `[Vec<ObjId>; 4]` から `[TaskQueue; 4]` に変えた（公開のフィールドの型が変わる）。`Vec` のままでは真ん中から抜くのも優先度の位置に入れるのも O(N) のまま。このフィールドは「crate の中のモジュールが共有するための pub」（`src/vm.rs` のホスト向けの口の節の注記）で、rubevy・rubevy_games・playground・移植キットのどこも読んでいない（grep で 0 件）。0.7.0 は 0.x の minor で、壊す変更をしてよい番号。CHANGELOG に書く。
- S6: 起きる順は「待ちの列に入った順」を保つ。期限の順ではない（本家の `mrb_tick` が待ちの列を頭から歩くのと同じ結果）。同時に期限が来た分だけを取り出して、入った順に並べ直す（k 個なら k log k）。
- S6: 指し示す番号（キーの後半）は 1 本の `u64` の通し番号で、4 本の列・期限の索引・待つ相手の索引で共有する。1 秒に 10 億回入れ替えても 500 年以上あふれない。
- S6: 期限の索引の鍵は、折り返さない tick（`tick_abs`）。`tick` は `pub` で `u32` の折り返しがあり、ホストや `idle` が直接動かすので、見るたびに差分（折り返し込み）を足して追いつく形にした（`abs_tick`）。`tick` は前にしか動かず、2^32 tick（4 ms なら約 200 日）動く前に必ず 1 度は見られる、が前提。
- S6: 数え上げの口 `TaskState::walked`（`#[doc(hidden)] pub`）を足した。テストが「1 回の費用」を時間でなく数で見るため。ホストに見せる数ではないので H3 の口とは別。
- S4: 計画書 H2 の段階表は「まず案の報告で止まる。実装は著者が案を見てから」だが、`release-0.7-plan.md` が S4 を 0.7.0 に入れ、著者がその範囲を認めた（2026-09-26）ので、案を下に書いたうえで計画書の第一候補（ホストが明示的に呼ぶ `Vm::unload`、番号を再利用しない空き枠）を実装した。止まる条件（安全に言えない場面を守れない）には当たらなかった — 指す側を全部挙げ、そのどれもが `unload` の走査に入っている。
- S4: 番号は再利用しない（計画書の第一候補）。代わりに 1 irep につき `VmIrep` 1 つぶん（208 バイト、中身の `Vec` は空）が残る。再利用するかは著者の判断に回す（報告に書く）。
- S4: 使っていないかの判定は `unload` の中で数える（参照の数は持たない）。まず走査し、使われていそうなら 1 度だけ回収してからもう 1 度走査する。回収できないとき（ネイティブの実行中、`GC.disable`）は回収せず「使用中」と答える — 間違うなら安全側。
- S4: `unload` できるのは `Vm::load` が返した番号だけ。`load_and_run`・`eval`・`require` が読んだものは番号を誰にも渡さないので表に載せない（載せると `eval` 1 回ごとに表の項目が 1 つ増え、誰も消さない）。
- S4: 返したプログラムの番号で `run_irep`・`task_spawn` を呼ぶと `ArgumentError`（"the program was unloaded"）。戻り値の無い `Vm::start` は panic（今でも存在しない番号では添字で panic する。それを明示の `assert!` にした）。
- S4: その番号を指す例外の記録（`@__bt`）は、`unload` の中で文字にして `@__btstr` に置く（`set_backtrace` が置く場所）。本家は backtrace が irep の参照数を 1 つ持つ（`copy_backtrace`、src/backtrace.c:24-39）ので例外が生きている間 irep が残るが、ここでは例外 1 つでプログラムを返せなくなるより、文字にして返すほうを選んだ。

## S5: `Exception#backtrace` にネイティブの名前（H5）

### 本家が何を出すか

`../../ref/mruby`（`4.1.0-rc2`、`c17ffcc24`）の `src/backtrace.c:47-95`（`pack_backtrace`）。callinfo を上から順に見て、
Ruby のフレーム（`ci->proc` が C 関数でない）はデバッグ情報が無ければ飛ばし、C 関数のフレームは `mid` が 0 なら飛ばし、
そうでなければ **その下で最初に見つかるデバッグ情報のある Ruby フレーム**の位置を借りる。1 つも無ければ
`loc.irep = NULL` で、文字にするとき（`decode_location`、`:140-170`）に名前なしの `(unknown):0` になる。
`Kernel#raise` は `mrb_f_raise`（`src/kernel.c:544-569`）が最初に `mrb->c->ci->mid = 0` として自分の名前を消すので出ない。

SabiRuby のネイティブはフレームを持たないので、例外を保存する `keep_backtrace`（`src/vm.rs`、run loop が `Err` を受けた
ところで呼ぶ）が見るのは Ruby のフレームだけだった。ネイティブの名前が入るのは `Vm::backtrace(Some(mid))`（`caller` が
使う）の先頭 1 つだけ — これが H5 の「2 つの backtrace の食い違い」。

### 確かめた入力と出力

同じスクリプトを本家（docker `kishima/mruby:4.1.0-rc2`、`mrbc -g` → `mruby -b`）と SabiRuby で走らせて比べた。
変更前に違ったのは次の形（抜粋）:

| スクリプト | 本家 | 変更前の SabiRuby |
|---|---|---|
| `Integer("zz")` | `["bt.rb:5:in Integer", "bt.rb:5"]` | `["bt.rb:5"]` |
| `def bar; [1].fetch(5); end` | `["bt.rb:7:in __fetch", "bt.rb:7:in bar", "bt.rb:9"]` | `__fetch` が無い |
| `[3,1].sort { raise "s" }` | `["bt.rb:18", "bt.rb:18:in sort!", "bt.rb:18"]` | `sort!` が無い |
| `[1].index { raise "i" }` | `…, "bt3.rb:2:in index", …` | `index` が無い |
| デバッグ情報なしの `Integer("zz")` | `["(unknown):0"]` | `[]` |
| デバッグ情報なしで `sort { x = caller }` | `[]` | `nil`（`caller` の数え方が 1 つずれる） |

同じだったもの: `raise` を名前に出さない、`1/0`（`OP_DIV` が直接投げる。C のフレームが無い）、`nil.zork`（`NoMethodError`
は VM が投げる）、mrblib の Ruby のメソッド（`each`、`map`、`Hash#fetch` — デバッグ情報が無いので両方で消える）。

### 作ったもの

`Vm::backtrace_record(natives)`（公開、足しただけ）が、例外の記録と `caller` の両方の元になる。記録の形は今までの
`[irep, pc, mid]` の 3 つ組の列に、ネイティブを `[-1, 0, mid]` として混ぜたもの。ネイティブは 3 か所で見つかる:

1. **例外を返したネイティブ**。`call_native_direct` / `call_closure_direct`（SEND がネイティブを呼ぶ唯一の道）で、
   戻りが `Err` のときだけ `keep_native_backtrace`（`#[cold]`）を呼び、その場のフレームとネイティブの名前で記録を作る。
   このときフレームはまだ呼び出しの形のまま（呼んだフレームの `pc` は SEND の直後）。run loop まで戻ってからでは名前が
   分からない（`native_mid` は入口でしか正しくない）。ネイティブの名前は、今まで `self.native_mid` から取っていた
   ところを、呼び出し側が知っている `mid` を引数で渡す形にした（`method_missing` のクロージャの道では `native_mid`
   が古いままだったので）。
2. **`Cci::Skip` のフレームの下**。ネイティブがブロックを呼ぶと `call_proc_inner` が `Cci::Skip` のフレームを積む。
   その 1 つ下のフレームの `pc` はまだそのネイティブを呼んだ SEND の直後にある — `Vm::boundary_name`（wait-anywhere で
   作った、待てない場所の名前を出す関数）と同じ読み方で、`send_before` がその名前を返す。`sort!`、`gsub`、`each_object`、
   ホストの関数がブロックを呼び返した場合、がここ。
3. **ネイティブのループのフレーム**（`LOOP_IREP`）。`index { }`・`rindex { }`・`Array.new(n) { }` は wait-anywhere で
   ブロックを自分のフレームから呼ぶようになり、そのフレームは呼ばれた名前を `mid` に持っている。ただし `catch { }` の
   ループ（`LOOP_CATCH`）は出さない — 本家の `catch` はデバッグ情報の無いバイトコード（`catch_iseq`）なので出ないから。

`backtrace_text` は、ネイティブの項目を次の（外側の）フレームのうちデバッグ情報のある最初のものの位置に置く。無ければ
`(unknown):0`。古い形の記録（ネイティブの項目の無いもの）も同じように読める。

### 捨てた案

- **run loop で記録を作ったあと、ネイティブを 1 つずつ差し込む**（例外が SEND の場所を通るたびに、記録の中の
  呼んだフレームの位置を探して挿入する）。`ensure` を通ると記録の後に命令が走り、`rescue` 済みで再び投げた古い例外にも
  差し込んでしまう。「この伝播で作った記録か」を覚える欄が要り、`rescue` で消す場所も要る。作った瞬間にネイティブが
  全部見えている上の形のほうが、状態を持たない。
- **ネイティブの名前の積み場（呼ぶたびに push/pop）**。`funcall` で入れ子になったネイティブまで本家どおりに出せるが、
  例外の無い普通のネイティブ呼び出しのたびに 2 回の書き込みが乗る。0.7.0 は通常時の性能を落とさない約束なので採らない。
  本家と違うのは `Method#call` で `+` を呼んだ例（本家 `in +`、SabiRuby `in call`）くらいで、これは下の表に書いた。

### 残った違い

`tests/custom/native_backtrace.rb`（本家の出力 `.rc.out` と SabiRuby の `.expected` を並べてある）の最後の 7 行:

| スクリプト | 本家 | SabiRuby | なぜ |
|---|---|---|---|
| `Class.new { raise }`、`Struct.new(:a) { raise }` | 下に `in new` | 無い | ブロックを `KeepSelf` のフレームで走らせ、ネイティブは返ってしまっている |
| `Module.new { raise }` | 下に `in initialize` | 無い | 同上 |
| `[1].delete(5) { raise }` | 下に `in delete` | 無い | 同上（ブロックのフレームを呼び出しの場所に積む） |
| `[1].instance_exec { raise }` | ブロックの行が `in instance_exec` | 名前なし | 本家は C 関数のフレームをブロックのフレームに書き換えて `mid` を残す。`__method__` も本家は `:instance_exec` を返す |
| `eval("raise 'ev'")` | `(eval):1:in eval` | `(eval):1` | 同上 |
| `1.method(:+).call(nil)` | `in +` | `in call` | ネイティブがネイティブを `funcall` で呼んだ分は数えない |

揃えるには、ネイティブに代わって積んだフレームに「下にネイティブがある」か「このフレームはネイティブの名前を名乗る」を
覚えさせることになる。`CallInfo` に欄を足すか `Cci` を増やすかで、どちらもフレームの形（毎回の push と return）に触る。
H5 の到達点（2 つの backtrace が同じことを言う、例外がネイティブの名前を持つ）はこれ無しで満たせるので、ここまでにした。

## S6: 待ちタスクの費用（H1）

### 着手前に読んだもの

`src/builtins/ext_task.rs`（main `2fe974e`）。計画書 3.1 の行番号（0.5.2 のもの）からはずれていたが、中身は計画書どおり:

- `q_insert`（`:70-79`）: ready の列は優先度の位置を頭から探して `Vec::insert`、ほかは `push`。
- `q_delete`（`:82-90`）: 4 本の列を順に `position` で探して `Vec::remove`。
- `is_queued`（`:100-102`）: 4 本を全部 `contains`。`Task#status` などのインスタンスメソッドは入口で必ずこれを呼ぶ（`live`）。
- `wake_sleepers`（`:277-300`）: 待ちの列を `clone()` して全部見る。先頭のガード（`wakeup_tick` がまだ来ていなければ返る）は効いている。
- `wake_join_waiters`（`:416-425`）・`wake_queue_waiters`（`:814-825`）: 待ちの列を `clone()` して、理由と相手が合うものを探す。
- `pending`（`:521-530`）: ready が空なら待ちの列を歩く。
- `Queue#num_waiting`（`:891-899`）: 待ちの列を `clone()` して数える。

### 先に順を固定した

計画書の既定「データ構造を変えても起きる順が変わらないこと。順が観測できるテストを先に足してから構造を変える」に従って、
`tests/task_scale.rs` の 7 本を**変更前のコードで**通してから構造に手を付けた。最初に書いた期待のうち 2 つは変更前の
コードと合わなかったので、コードのほうを正として期待を直した:

- `join` の戻り値は、実際に待った場合 `nil`（待つ前の結果を返す。`docs/design/gems.md` に書いてあるとおり）。
  「誰が先に起きたか」だけを見るテストにした。
- 6 回回したあとの `Task.stat` で、すぐ終わるタスクは既に dormant の列にいる。

固定した順: 同時に期限が来た sleeper は**待ちの列に入った順**に ready になる（期限 30 ms の `a` が期限 20 ms の `c` より
先に眠っていれば、時計が両方を越えたとき `a` が先）。`Task#resume` で早く起こしたタスクの期限は、次に時計が
それを越えるまで `wakeup_tick` に残る（`Task.stat[:wakeup_tick]` で見える）。同じキューを待つ読み手は待った順に 1 つずつ、
`close` は全員を順に。タイムアウトつきの `pop` は、期限とプッシュのどちらか早いほうで起きる。`join` の待ち手は join した順。
ready の列は優先度順・同じ優先度は来た順、`priority=` はその優先度の最後に並び直す。`Task.list`・`Task.stat`・`Task.get` は
各列をその順に並べる。

### 数え方と、変更前の数

時間ではなく「スケジューラが 1 つずつ見た・動かした列の要素の数」を数える口 `TaskState::walked` を足し、変更前のコードの
歩く場所すべてに足し込みを入れて測った（`q_insert` の位置探し、`q_delete` の探索と `Vec::remove` のずらし、`is_queued`、
`wake_*` の `clone` と走査）。`pending` だけは `&Vm` を取る公開の口（`Vm::task_pending`）なので数えていない。
変更前のコードに入れた足し込みはこのコミットには残っていない（構造ごと消えた）。

2 つの形で、1 回の費用を 100 台と 1000 台で比べた（`tests/task_scale.rs` の最後の 2 本）:

- **待っているだけのタスクがいる**（`crowd(n)`）: 自分のキューを `pop` して待つタスク n 本、遠い未来まで眠るタスク n 本、
  それとは別に「プッシュで起きて 1 回走ってまた待つ」タスクと「1 tick ごとに期限で起きる」タスク。
  測るのは、ホストのプッシュ 1 回 + その 1 回の実行、tick 1 つ + その 1 回の実行。
- **全員が ready**（`ready_crowd(n)`）: n 本が `loop { Task.pass }`。1 本の 1 回と、`Task#status` 1 回。

| | 100 台 | 1000 台 |
|---|---|---|
| 変更前: プッシュ 1 回 | 406 | 4006 |
| 変更前: tick 1 つ | 406 | 4006 |
| 変更前: ready の 1 回 | 200 | 2000 |
| 変更前: `Task#status` | 100 | 1000 |
| **変更後: プッシュ 1 回** | **1** | **1** |
| **変更後: tick 1 つ** | **1** | **1** |
| **変更後: ready の 1 回** | **0** | **0** |
| **変更後: `Task#status`** | **0** | **0** |

変更前は 1 回がちょうど台数に比例していた（プッシュ 1 回は、`wake_queue_waiters` の `clone` と走査で 2n+2、
起きたタスクの `q_delete` と ready への `q_insert`、走った後にまた待つときの `q_delete`、で約 4n）。変更後に残る 1 は
「起こした 1 本」を数えたもの。

変更後の数に入っていないのは `BTreeMap` の中の仕事（探索・挿入・削除は木の高さ、つまり log n）。これは「1 つずつ歩く」
ではないので数えていない。O(N) から O(log N) になった、が正確な言い方。

### 作ったもの

- `TaskQueue`（`src/vm.rs`）: 鍵 `(優先度, 通し番号)` の `BTreeMap`。ready 以外は優先度の欄を 0 にして「来た順」だけになる。
  頭は `first_key_value`、抜くのはタスクが覚えている鍵で `remove`。
- `TaskData` に 3 つ: `queued`（どの列のどの鍵にいるか）、`sleep_key`、`wait_key`。`is_queued` は `queued.is_some()` になった。
- `TaskState::sleepers`: 鍵 `(折り返さない期限, 通し番号)`。待ちの列に入るときに、理由が SLEEP か QUEUE で期限があれば入れる
  （変更前に `wake_sleepers` が見ていた条件そのまま）。`wake_sleepers` は頭から期限の来た分だけ取り出し、通し番号で
  並べ直して ready にする。次の期限は索引の頭。
- `TaskState::waiters`: 鍵 `(待つ相手の ObjId, 通し番号)`。QUEUE ならキュー、JOIN なら join しているタスク。1 本の表で
  足りるのは、キューとタスクが別のオブジェクトだから。プッシュは `range` の頭の 1 つ、`close` と join は範囲全部。
  `num_waiting` はそのキューの範囲だけを数える（k 本待っていれば k）。
- `pending` は「ready が空でない、または期限つきの待ちがある」で、歩かない。

索引から消す場所は `q_delete` 1 か所に集めた。状態を変える道はすべて `q_delete` → 欄の書き換え → `q_insert` を通る
（`set_status`、`wake_*`、`Task#priority=`、`reinit_context`）。`Task#resume` は理由と期限を消してから `set_status` を呼ぶが、
消すのに使う鍵はタスクが覚えている鍵なので、欄を先に書き換えても索引は正しく抜ける。

**GC.** 索引が持つのは待ちの列にいるタスク（根。`gc_mark_roots` が `queues[1..]` をマークする）と、それらが待つ相手
（タスクの辺としてマークされる: `docs/design/gc.md` の Task の行「the queue it waits on」「the task it joins」）だけなので、
根を足す必要は無かった。dormant の列は弱いままで、`retain` の形だけ変わった。`SABIRUBY_GC_STRESS=1` で
`tests/task_scale.rs`・`tests/task.rs`・`tests/wait_anywhere.rs` を通した。

### 捨てた案

- **`Vec` のまま、タスクに列の中の位置を覚えさせる**。抜くのは O(1) になるが、`Vec::remove` のずらしは残り、位置が
  ずれるたびに覚え直す必要がある。ready の列を優先度ごとの `VecDeque` に分ける案も、真ん中から抜く（`Task#suspend`、
  `Task#close`）が残る。`BTreeMap` 1 つで全部 log n になるほうが、場合分けが少ない。
- **ヒープ（`BinaryHeap`）で期限を持つ**。計画書の候補の 1 つ。途中で抜く（早く起こされた、プッシュで起きた）ができないので、
  古い項目を残して取り出すときに捨てる形になる。取り出すときにタスクがまだ同じ理由で待っているかを確かめる必要があり、
  その `ObjId` がもう別のオブジェクトになっている（回収されて使い回された）場合まで考えることになる。`BTreeMap` なら
  抜けるので、索引の中身はいつも「今待っているタスク」だけ。

  baseline を下回らない（`mrbtest_no_regression`。mruby-task の `gem_task` 43・`gem_queue` 23・`gem_gc_task` 6 を含む）。

  `tools/bench_ab.sh`（タスクを使わないベンチが遅くなっていないこと）は、本体の合図を待つ。

## S4: irep を返す（H2）

### 誰が irep を指しているか

`IrepId` は `ireps` の添字（`src/object.rs:40`、`pub type IrepId = usize`）。`grep IrepId` と `ireps.push` で全部当たった:

| 持ち主 | どこ | 生きている間 |
|---|---|---|
| フレーム（`CallInfo::irep`） | `Vm::ci`（走っている文脈）と `Vm::contexts[*].ci`（止まっている fiber・task） | そのフレームが積まれている間 |
| Proc（`ProcData::irep`） | ヒープ（`src/object.rs:123`）。ブロック、lambda、`def` でクラスのメソッド表に入ったもの、`define_method`、`Method` オブジェクト、task と fiber を作った Proc（`Context::proc_`） | Proc が回収されるまで |
| 子の irep（`VmIrep::reps`） | 同じ `load` で読んだ木の中だけ（`load` が `offset` を足す） | 木と一緒 |
| 例外の記録（`@__bt` の `[irep, pc, mid]`） | 例外オブジェクトの隠しインスタンス変数（S5 で作った形） | 例外が回収されるまで |
| ホストが持つ番号 | `Vm::load` の戻り値。rubevy の `ScriptWorld` の「内容 → `IrepId`」の表 | ホスト次第 |
| 記録のイベント（`TraceEvent::Raise` / `CatchLook` の `irep`） | `Vm::trace`（デバッガ向け、既定は無効） | ホストが取り出すまで。表示にしか使わない |
| `eval` の使い捨て、`Binding` の `wrap_lvspace` | `ext_eval.rs:74,102,172`、`ext_binding.rs:43` | 誰も返さない（下の「気づいた点」） |

`VmIrep` 自体には書き込みが無い（rubevy R2 の worklog が確かめたとおり。`merge_lvar` が触るのは `wrap_lvspace` の irep だけ）。
メソッドキャッシュ（`method_cache`）は Proc の `ObjId` を持つだけで irep は持たない。

### 案

1. **ホストが呼ぶ `Vm::unload`、その場で走査（採った）**。`load` が読んだ範囲を覚えておき、`unload` はすべての文脈のフレームと、
   ヒープの Proc を 1 回ずつ見る。何か見つかれば 1 度回収して見直す（終わった task の Proc のように、ゴミだが回収されていない
   ものがよくある）。代償: `unload` 1 回につきフレームとヒープの走査 1 回、使われていそうなら回収 1 回。普段の実行（命令の
   ループ、呼び出し、GC のマーク）には何も足さない。
2. **参照の数を持つ**（本家の `mrb_irep_incref` の形）。Proc を作るとき・回収するとき、フレームを積むとき・降ろすときに数える。
   `unload` は O(1) で答えられ、数が 0 になった時点で自動で返すこともできる。代償: フレームの push と pop は命令のループの
   いちばん熱いところで、1 回ごとに `ireps[i]` への書き込みが 2 つ乗る（別の配列に数を置いてもキャッシュの行が 1 本増える）。
   0.7.0 の「通常時の性能を落とさない」に正面から当たる。本家が数えているのは Proc と backtrace で、フレームは Proc を
   経由するので数えていない — SabiRuby はフレームが `irep` を直接持つので、同じ形にはならない。
3. **GC のマークで数える**（ホストは「もう使わない」と言うだけ、実際に返すのは次の回収）。マークのときに Proc とフレームの
   `irep` に印を付け、印の無い「手放された」木を掃除のときに返す。代償: マークに Proc 1 つごとの書き込みが 1 つ乗る
   （手放された木が無いときは飛ばせる）。ホストは「いつ返ったか」を知る口が別に要る。GC の規則（`docs/design/gc.md`）に
   新しい種類の根と掃除が増える。案 1 と比べて得るのは「ホストがもう一度聞かなくてよい」ことだけで、その分 GC が複雑になる。
4. **番号を再利用する**（案 1 の変形。`HostStore` の空き番号の列と同じ）。`ireps` の長さも増えなくなる。代償: 古い番号を
   持ち続けたホスト（`ScriptWorld` の表から消し忘れたもの）が、同じ番号の**別のプログラム**を走らせる。計画書が名指しで
   避けた事故。

案 1 を採った。計画書の第一候補（ホストが明示的に呼ぶ、VM は勝手に消さない、番号を再利用しない空き枠）で、熱い道に何も
足さず、GC の規則も変えない。

### 番号を再利用しない代償（測った）

`size_of::<VmIrep>()` は 208 バイト（`tests/unload.rs` の中で一時的に出して確かめた）。返した irep はこの大きさの空の項目
（`Vec` はすべて空、`filename` は `None`）として残る。`tests/unload.rs` の差し替え 30 回のあと、`ireps` の項目は 605、
中身のあるものは 541 で一定（差し替えのたびに空の項目が 2 つ = 416 バイト増える。このスクリプトは top level と `loop` の
ブロックの 2 irep）。返るのは `iseq`・`catch`・`pool`・`syms`・`reps`・`lv`・`lines`・`filename` が指していたもの全部。
rubevy の R2 の計測では、この形のスクリプト 1 本の irep が 0.75 kB（208 × 2 の本体を含む）だったので、小さなスクリプトでは
返る量と残る量が同じくらいになる。スクリプトが大きいほど残る割合は小さい。**番号を再利用して残りを 0 にするかは
著者の判断**（案 4 の代償と引き換え）。

### 作ったもの

- `Vm::irep_loads: BTreeMap<IrepId, (IrepId, IrepId)>`（非公開）: `Vm::load` が答えた番号 → そのプログラムの irep の範囲。
  `load` は範囲をまとめて `push` するので、木は連続した範囲になる。
- `Vm::unload(irep) -> Result<(), UnloadError>`（公開、足しただけ）と `UnloadError { NotLoaded, StillInUse }`（`lib.rs` から再輸出）。
- `Vm::load_ireps`（crate の中）: 表に載せない `load`。`eval`・`require`・`load_and_run` はこちらを使う。
- `Vm::irep_gone`: 中身の無い項目（返したもの、または範囲の外）。`run_irep` と `task_spawn` はこれを `ArgumentError` に、
  `start` は `assert!` にする。コンパイラが作る irep は必ず命令を持つので、空の `iseq` は返したものだけ。

**GC との関係.** 走査は GC の外で、GC に何も足していない。`unload` が回収するのは「ネイティブが走っていない
（`native_active == 0`）かつ `GC.disable` でない」ときだけで、これは `GC.start` がその場で回収する条件と同じ
（`docs/design/gc.md`「When it runs」）。テストで一度踏んだ: ホストの 1 行を走らせた戻り値を登録せずに `unload` を呼ぶと、
`unload` の回収でその値が消える（`$err.backtrace` の配列が別のオブジェクトになって `inspect` が `BasicObject` の
`NoMethodError` を投げた）。これは既存の約束（ホストが持つ値は次に VM を呼ぶまでしか安全でない。`gc.md`「Contract for
native code」）どおりの振る舞いで、テストの補助関数の順番（`inspect` してから `unload`）を直した。`unload` の rustdoc に
「回収が走ることがある」と書いた。

### テスト（`tests/unload.rs`、6 本）

1. **差し替えを 30 回**: スクリプト（`$inbox.pop` を待つ task）を毎回違う本文で読み、新しい task を走らせ、古い task を
   `terminate` してホストの登録を外し、古いプログラムを `unload`。中身のある irep の数とその大きさが 30 回とも最初と同じ。
   本文は長さを揃えた（`"0001"` の形。数字の桁で `OP_LOADI` の形が変わり、命令列が 2 バイト違ったため）。
2. **task が使っている間**: 待っている間は `StillInUse`、`terminate` しても**ホストがまだ task を持っていれば** `StillInUse`
   （task の Proc がプログラムの top level）、登録を外すと `Ok`、2 回目は `NotLoaded`。
3. **ブロック・メソッド・fiber**: `$keep = proc {}` は `nil` にするまで、`def` したメソッドは `remove_method` するまで、
   途中で止まった fiber は `Fiber` オブジェクトを手放すまで（Proc を手放しても fiber のフレームが指している）`StillInUse`。
4. **自分の下で走っている**: ホストの関数（`define_closure`）の中から、その関数を呼んだプログラムを `unload` すると
   `StillInUse`（呼んだフレームが下にある。回収もしない — ネイティブの実行中）。
5. **例外の backtrace**: プログラムの中で投げた例外を `$err` に残して `unload` しても、`$err.backtrace` は前と同じ文字列。
6. **返した番号**: `run_irep`・`task_spawn` は `ArgumentError`、次の `load` は別の番号、ブロックの番号（`root + 1`）や
   でたらめな番号は `NotLoaded`。

`SABIRUBY_GC_STRESS=1` でも 6 本通る（差し替えのテストで回収が 191 回。無しでは 32 回 — 30 回の `unload` がそれぞれ
1 回回収している。終わった task の Proc が回収前に残っているため）。

### rubevy の側（この repo からは触らない）

`ScriptWorld` の「内容 → `IrepId`」の表（R2）は、同じ本文を 2 本目の task が使うための表なので、`unload` した番号を
表から外す必要がある。外し忘れると、同じ本文が戻ってきたときに返した番号で `task_spawn` して `ArgumentError`（再利用
しないので、別のプログラムは走らない）。`replace_script` のあとで古いプログラムを `unload` するのは、その本文を使う
task が他に無いときだけ — これは `StillInUse` が教える。rubevy の次の計画で。

## 気づいた点

- **`eval` と `Binding` は呼ぶたびに irep を足し、誰も返さない**（VM）。`ext_eval.rs:74,102,172` は毎回 `load_ireps`、
  `ext_binding.rs:43`（`wrap_lvspace`）は `binding` 1 回ごとに 1 つ `push`。ループの中で `eval` や `binding` を呼ぶ
  スクリプトは、H2 の差し替えと同じく上限なく積む。`unload` の走査は 1 回がヒープ全体なので `eval` のたびには呼べない。
  直すなら、`eval` の木を「その `eval` の Proc が回収されたら返す」形（案 3 の、VM が自分で持つ版）で。
- **`load_and_run` で読んだものは `unload` できない**（VM／rubevy）。番号を返さないので当然だが、rubevy の
  `ScriptWorld::load_and_run`（`rubevy/src/lib.rs:2144`）と Factory（`rubevy_games/factory/src/data.rs:551`、`main.rs:3623`）
  はこれを使っている。起動時に 1 度走らせる層やデータなら問題ないが、何度も読み直すなら `load` + `run_irep` + `unload`
  の形に。rustdoc の `load_and_run` にそう書いた。
- **`__method__` が本家と違う**（VM、本家との差）。本家は `instance_exec` のブロックと top level の `eval` の中で
  `__method__` が `:instance_exec` / `:eval`（C 関数のフレームを書き換えて `mid` を残すため）、SabiRuby は `nil`。
  S5 の残った違い（backtrace のブロックの行に `in instance_exec` が無い）と同じ根。docs に書いていないので `gems.md` の
  差の一覧に載せるかは本体の判断。
- **`method_missing` がクロージャのときの `native_mid`**（VM、`src/vm.rs` の `op_send` の「メソッドが無い」の分岐）。
  そこでは `native_mid` を設定せずに `call_closure_direct` を呼んでいた。S5 で名前を引数で渡す形にしたので backtrace は
  正しく `method_missing` になったが、`native_mid` 自体は前の呼び出しの名前のまま。クロージャが `native_mid` を読むと
  （`Struct` のアクセサの流儀）古い名前を見る。S2（段階 A、`funcall` の同じ分岐）と近い場所なので、段階 C の突き合わせで見る。
- **記録のイベントの `irep`**（VM、`src/inspect.rs:57,59`）。`unload` のあとは空の項目を指すので、デバッガが行を
  引くと `None` になる。表示だけの話で壊れはしない。
- **rubevy の文書**（rubevy）。`docs/host-api.md`「A parked task costs nothing」は命令の予算の話として正しかったが、
  S6 でスケジューラの実時間の意味でも正しくなった（台数に比例する歩きが無くなった）。ベンチの後に rubevy 側で書き足す。
  `ScriptWorld` の表と `unload` の話は上の「rubevy の側」。
- **本の素材**（本）。本家 mruby-task は待ちの列を頭から歩くので、同時に期限が来た sleeper は「期限の順」ではなく
  「眠った順」に起きる（30 ms 眠った `a` が 20 ms の `c` より先に眠っていれば先に起きる）。索引に替えるときこれを保つには、
  期限で取り出したあと入った順に並べ直す必要があった。
- **`unload` 1 回に回収 1 回**（rubevy）。rubevy の差し替えの形（古い task を止めて手放し、すぐ `unload`）では、止めた
  task の Proc がまだ回収されていないので、`unload` が毎回全体の回収を 1 回走らせる。1 回の時間はヒープの大きさ次第で、
  測っていない（本体の合図待ちのベンチで一緒に見るなら、差し替えの瞬間のフレーム時間）。
