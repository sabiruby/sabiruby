# Numbers

The defaults and limits the VM carries, each with where it is changed and where it came from
(`/home/kishima/book/CLAUDE.md`: a number is a default a user can change, and it says where it
came from). This list starts with 0.7.0; the older numbers are to be added (`docs/plans/`, R10).

| number | default | changed with | where it came from |
|---|---|---|---|
| `TASK_INDEX_FROM` — waiting tasks from which the scheduler indexes them (deadlines, awaited objects) instead of walking the waiting queue | 30 | `Vm::task_set_index_from` (`TaskState::index_from`) | Measured 2026-09-27 (`worklog/2026-09-27-release-0.7-bench.md`): two tasks playing queue ping-pong 200,000 times beside N tasks waiting on queues nobody pushes to, indexed against walking, 2 rounds of 5, best. Walking was 2.0% faster at N = 10, the same at 30 (+0.4%), 9.6% slower at 100, 52% at 300, 160% at 1000. |
| time limit per test file of `tools/edge_compare.sh` (the comparison with mruby/edge) — not the VM's, the tool's | 30 s | `tools/edge_compare.sh --timeout SECONDS` (`tools/edge-compare/run.py`) | Taken from mruby/edge so that both are cut off at the same point: `--timeout` of its `scripts/mruby_spec_report.py` defaults to 30 and its `tests/mruby_spec/mod.rs` kills the child after 30 seconds (`d15d933`, 2026-10-14). Not measured here; every file takes well under a second on SabiRuby (`docs/verification/edge-compare/`). |
| `OUTPUT_BLOCK` — bytes of the program's output the `sabiruby` command holds before writing them, when standard output is not a terminal (on a terminal every write is flushed) — not the VM's, the command's | 64 KiB | the constant in `cli/src/main.rs` (no switch) | Where 64 KiB came from: unknown; chosen with the output sink (`041e096`), not measured. The reference leaves the size to C stdio: `src/print.c` writes with `fwrite` and flushes only when `isatty` says the stream is a terminal (4.1.0-rc2). The size changes only when the bytes appear, not which bytes or their order. |

The numbers of the rc2 sweep's tools (`tools/rc2_sweep/`, `verification/rc2-sweep/`; not the VM's).
Where a source is "unknown", the record says what was done but not why that number:

| number | default | changed with | where it came from |
|---|---|---|---|
| time limit per call of the X1 sweep | none: given every time; 5 s is the value used | `sweep.py run --timeout SECONDS` | Measured 2026-10-18 (`worklog/2026-10-18-rc2-sweep.md` "1 呼び出しごとの時間の上限"): the first full run had 60 s (where 60 came from: unknown); of about 960,000 calls that finished, the slowest took 0.112 s. Only `(1..)`'s calls (`all?`, `count`, `sum`, …) did not end, and that receiver was run again with 5 s, more than 40 times the slowest call that finished, so a call that reaches it does not end rather than is slow. The whole sweep with 5 s (2026-10-18, `worklog/2026-10-18-rc2-sweep-fixes.md` Y0, two runs beside other work): the slowest call 0.475 s, no call reached the limit outside `(1..)`. The limit starts at a chunk's `ready` line, not at its start (before Y0 it counted the reference's reading of a large chunk, about 4 s, and 5 s timed out every call of String and Array). |
| time limit per program of X2 | none: given every time; 60 s is the value used | `programs.py run --timeout SECONDS` | Where 60 came from: unknown. Checked after the run (2026-10-18, same worklog "X2"): the slowest program that finished took 1.33 s (SabiRuby, `gem_regexp_syntax.rb`); only `test_NOP_empty_loop.rb`, which does not end on purpose, reached the limit. |
| processes at a time per side, X1 and X2 | a quarter of the CPUs (6 on the 24-CPU machine), at least 1 | `sweep.py run --jobs N`, `programs.py run --jobs N` | Chosen 2026-10-18 (same worklog "走らせ方で詰まったこと"): both sides together take half the CPUs, the other half left because another agent was using Docker on the same machine. Not measured for speed. |
| address space per process of the X1 sweep (`ulimit -v`) | half of `MemAvailable`, divided by the processes running at once (2 × jobs); about 1 GB on that machine | `sweep.py run --mem BYTES` | Chosen 2026-10-18 (same worklog): the formula is recorded, why half: unknown. |
| `SW_YIELD_MAX` — calls of the sweep's block before the call is stopped (`SwStop`) | 9**3 = 729 | `tools/rc2_sweep/prelude.rb` (then `sweep.py cases` again) | Derived from the call table (`prelude.rb`'s comment, same worklog): the receiver or argument with the most elements is `1...10` (9 values) and a call takes at most 3 arguments, so no call that ends yields more (`product` and the like). A call that reaches it iterates towards 2**70 or Infinity, or forever. Changing the table (a longer value, more arguments) changes it. |
| three arguments: an orthogonal Latin square `(a, b, (a + b) mod 22)` instead of every triple | 484 rows per method (as many as two arguments; every triple would be 10,648) | `tools/rc2_sweep/cases.py` `arg_rows` (22 = `NVALS`, the plan's 22 values; 3 = `MAXARGS`, the plan's "0 to 3 arguments") | Derived (same worklog "組み合わせの数と上限"): every pair of values appears once in every pair of positions. Why every triple (22 times more three-argument calls) was not run: unknown; it was not measured. |
